5. Database Migration Plan
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&&
Database migrations must be performed in a way that keeps the application 
compatible with the database.

The preferred sequence is:

Backward-compatible migration
          ↓
Run migration
          ↓
Deploy new application
          ↓
Health check
          ↓
Verify application

For larger schema changes, the recommended approach is:

Expand
  ↓
Migrate
  ↓
Contract

The database should not be changed in a destructive way 
that makes rollback of the application impossible.

Application rollback and database rollback are treated as separate concerns.

###############################################################################################
4. Rollback Plan
############################################################################################
The deployment and rollback flow is:

                 CI
                 ↓
          Docker Image
                 ↓
                GHCR
                 ↓
             Deployment
                 ↓
             /health
             /     \
           OK       FAIL
           ↓          ↓
       Keep v2    Rollback
                     ↓
                    v1

If the new application version fails its health check
 or has a critical problem, the deployment should be rolled back 
 to the previous known-good Docker image.

For example:

Previous version:
ghcr.io/aymenwahas/backend-api:a82f921

New version:
ghcr.io/aymenwahas/backend-api:d20683e

If the new version fails:

d20683e
   ↓
Failure
   ↓
Rollback
   ↓
a82f921

The previous image is used because it represents the 
last known-good application version.
