13. Delivery Semantics
----------------------

The worker implements an at-least-once processing model.

Reason:

    Message is consumed
        |
        v
    Processing
        |
        +---- success ----> XACK
        |
        +---- failure ----> remains Pending
                              |
                              v
                          XAUTOCLAIM
                              |
                              v
                            Retry

The same business event may therefore be delivered more than once.

Idempotency is used to make duplicate processing safe.


14. Queue vs Pub/Sub vs Stream
------------------------------

Queue:

    Messages are normally processed by one consumer.

Pub/Sub:

    Messages are delivered to active subscribers and are generally
    not centered around persistent pending-message processing.

Stream:

    Messages are stored in an ordered stream and can be consumed
    through Consumer Groups with acknowledgement and pending tracking.

This project uses Redis Streams because the worker requires:

    - Consumer Groups
    - ACK
    - Pending message tracking
    - Retry
    - XAUTOCLAIM
    - DLQ support


15. Ordering
------------

Redis Stream entries have ordered IDs.

However:

    Stream order != guaranteed processing completion order

With multiple consumers or retries, a later event may complete before
an earlier event.

The current application has one notification consumer, so the current
deployment does not demonstrate parallel consumer ordering issues.


16. Replay
----------

Redis Stream entries are not automatically deleted by XACK.

XACK removes the message from the Pending Entries List.

The application currently has no explicit replay command or replay API.

Therefore:

    Replay workflow: Not implemented


17. Schema Evolution
--------------------

    Schema versioning: Not implemented


18. Outbox Pattern
------------------

The current task creation flow performs:

    PostgreSQL INSERT
        |
        v
    Redis event publish

These are separate operations.

Failure window:

    PostgreSQL INSERT succeeds
        |
        v
    Redis publish fails
        |
        v
    Task exists but event is missing

This is a dual-write consistency gap.

The Outbox Pattern would store the event in PostgreSQL in the same
transaction as the business change and publish it asynchronously.

24. Remediation List
--------------------

R1 - Outbox / Dual Write Gap
----------------------------
Priority: High

Problem:

    PostgreSQL task creation and Redis event publishing are separate
    operations.

Risk:

    Task can be committed while its event fails to publish.

Remediation:

    Add an Outbox table and publish pending outbox events asynchronously.


R2 - Explicit Replay Workflow
-----------------------------
Priority: Medium

Problem:

    No application-level replay command exists.

Remediation:

    Add a controlled replay mechanism for selected stream ranges or
    DLQ messages.


R3 - Event Schema Versioning
----------------------------
Priority: Medium

Problem:

    Events do not contain an explicit schema version.

Remediation:

    Add an event version field and define backward-compatible schema
    evolution rules.


R4 - DLQ Duplicate Protection
-----------------------------
Priority: Medium

Problem:

    If DLQ insertion succeeds but XACK fails, the same failed message
    could potentially be written to the DLQ more than once.

Remediation:

    Add DLQ idempotency using the original message ID.


R5 - Graceful Worker Shutdown
-----------------------------
Priority: Medium

Problem:

    The application starts the worker with context.Background().

Remediation:

    Use an application lifecycle context and cancel the worker during
    graceful server shutdown.


R6 - Consumer/Partition Scaling
-------------------------------
Priority: Low

Problem:

    Current implementation uses one consumer for the notification group.

Remediation:

    Run multiple consumers when throughput requirements increase and
    explicitly document ordering guarantees.
